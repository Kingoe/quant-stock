# 迭代流程

本文档定义每一轮功能开发、修复和文档调整都必须遵守的流程。目标是保证项目持续可验证、可追踪、可回滚，避免功能越做越偏。

## 1. 适用范围

以下情况都必须遵守本文档：

- 新增功能
- 修复问题
- 调整架构
- 修改策略规则
- 修改前端页面
- 修改数据流程
- 修改测试范围
- 修改项目文档

如果只是回答问题、阅读代码、做纯分析，可以不进入完整迭代流程。

## 2. 标准流程

每轮迭代必须按以下顺序执行：

1. 按 `docs/TASK_PLAN.md` 的里程碑顺序和任务 ID 顺序，选择下一个可执行的小范围任务。
2. 将任务状态更新为 `In Progress`。
3. 明确本轮验收标准。
4. 先补充或确认测试用例。
5. 实现功能或文档变更。
6. 运行对应验证。
7. 验证通过后，将任务状态更新为 `Done`。
8. 更新 `docs/CHANGELOG.md`。
9. 如有需要，更新架构、测试用例或项目约束文档。
10. 提交 Git，提交信息要说明本轮完成内容。

## 3. 验收标准

每轮迭代开始前，必须明确“怎样算完成”。

验收标准可以包括：

- 哪些测试必须通过。
- 哪些接口必须可用。
- 哪些页面必须能正常打开。
- 哪些报告必须能生成。
- 哪些文档必须同步更新。
- 哪些边界不能被破坏。

没有明确验收标准的任务不能直接开始实现。

## 4. 任务顺序规则

任务选择不是随机的。默认必须按照 `docs/TASK_PLAN.md` 中的里程碑顺序和任务 ID 顺序推进：

```text
M1-1 -> M1-2 -> M1-3 -> ...
M2-1 -> M2-2 -> M2-3 -> ...
```

选择任务时应遵守：

- 优先选择当前里程碑中第一个 `Not Started` 或 `In Progress` 的任务。
- 当前里程碑未完成前，不跳到后续里程碑。
- 同一里程碑内，默认按任务 ID 从小到大执行。
- 如果某个任务被阻塞，先标记为 `Blocked`，写明原因，再选择同一里程碑中下一个不依赖它的任务。
- 如果确实需要跨里程碑提前做某个任务，必须在 `docs/TASK_PLAN.md` 中写明原因。

允许例外的情况：

- 当前任务依赖外部资源，暂时无法继续。
- 后续任务是为了验证当前任务所必需的最小配套工作。
- 文档、测试或基础设施修正会影响后续所有任务。
- 用户明确要求调整优先级。

例外不能口头决定，必须同步记录到任务规划或更新日志中。

## 5. 验证要求

不同类型任务需要不同验证方式。

### 后端任务

必须至少运行相关后端测试。

常见验证：

```text
pytest
pytest backend/tests/指定测试文件.py
```

如果任务涉及 API，还需要本地启动后端并验证接口返回。

### 前端任务

必须至少运行相关前端测试或构建。

常见验证：

```text
npm test
npm run build
```

如果任务涉及页面，还需要打开本地页面进行人工检查。

### 数据任务

必须验证：

- 测试数据能跑通。
- 缺失数据有清晰提示。
- 不依赖实时数据完成单元测试。
- 不产生重复或脏数据。

### 策略和回测任务

必须验证：

- 固定测试数据结果可重复。
- A 股交易限制被正确处理。
- 没有未来函数。
- 指标计算结果可解释。

### 文档任务

必须验证：

- 相关文档之间不矛盾。
- 任务状态和更新日志同步。
- 新增规则能在项目约束或迭代流程中找到。

## 6. 文档更新门禁

每轮迭代结束前必须检查：

- `docs/TASK_PLAN.md` 是否更新任务状态。
- `docs/CHANGELOG.md` 是否记录本轮变更。
- 如果架构变化，是否更新 `docs/TECHNICAL_ARCHITECTURE.md`。
- 如果测试范围变化，是否更新 `docs/TEST_CASES.md`。
- 如果项目边界、风格或规则变化，是否更新 `docs/PROJECT_CONSTRAINTS.md`。
- 如果迭代方式变化，是否更新本文档。

## 7. 提交门禁

提交前必须满足：

- 本轮任务状态已更新。
- 本轮验证已执行。
- 验证失败不能标记任务为 `Done`。
- 更新日志已同步。
- Git 工作区只包含本轮相关改动。

如果验证无法运行，必须在最终说明和更新日志中明确原因。

## 8. 任务粒度

每轮任务应该尽量小。

推荐粒度：

- 一个后端模块。
- 一个 API。
- 一个页面。
- 一个数据加载器。
- 一个因子计算模块。
- 一组强相关测试。
- 一次文档规则调整。

避免一轮同时做：

- 数据源、回测、前端页面、报告导出全部混在一起。
- 大量无关重构。
- 同时修改策略逻辑和展示逻辑但没有测试隔离。

## 9. 失败处理

如果验证失败：

1. 不提交未完成结果，除非需要保存明确的中间状态。
2. 不把任务标记为 `Done`。
3. 在 `docs/TASK_PLAN.md` 中标记为 `Blocked` 或保持 `In Progress`。
4. 记录失败原因和下一步处理方式。

## 10. 每轮完成模板

每轮结束时，最终说明应包含：

```text
完成内容：
- ...

验证：
- ...

文档：
- ...

提交：
- ...
```

如果没有提交，需要说明原因。
