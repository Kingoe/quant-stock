# 架构决策记录

本文档记录已经做出的重要技术和产品决策。后续如果推翻或调整这些决策，必须新增记录说明原因。

## ADR-001：第一阶段不做自动下单

**日期：** 2026-05-09

**决策：** 第一阶段只做选股辅助、回测、调仓建议和可视化，不接券商自动下单。

**原因：**

- 自动交易涉及合规、券商接口、实盘风控和异常处理，复杂度高。
- 当前更重要的是验证策略和数据流程。
- 人工确认交易可以降低早期系统错误带来的资金风险。

**影响：**

- 第一版不实现 broker 模块的真实下单能力。
- 页面和报告必须提供清晰的人工确认信息。
- 后续只有在模拟运行稳定后，才评估券商接口。

## ADR-002：第一版使用中证 800 作为基础股票池

**日期：** 2026-05-09

**决策：** MVP 使用中证 800 作为基础股票池。

**原因：**

- 覆盖大盘和中盘股票，选择空间足够。
- 比全 A 更容易控制流动性和财务异常风险。
- 比沪深 300 更有弹性，适合多因子选股。

**影响：**

- 股票池过滤和回测优先围绕中证 800 构建。
- 全 A 选股作为后续增强，不进入 MVP。

## ADR-003：第一版采用周频调仓

**日期：** 2026-05-09

**决策：** MVP 使用每周一次调仓。

**原因：**

- 周频比日频更适合个人人工确认。
- 交易频率较低，手续费和滑点影响更容易控制。
- 可以减少盯盘压力。

**影响：**

- 回测引擎优先支持周频调仓。
- 前端调仓页以“本周建议”为核心。

## ADR-004：后端使用 FastAPI

**日期：** 2026-05-09

**决策：** 后端 API 使用 FastAPI。

**原因：**

- Python 生态适合数据处理和量化研究。
- FastAPI 适合轻量 API 服务，类型提示和接口文档友好。
- 后续可以自然服务 React 前端。

**影响：**

- 后端模块围绕 FastAPI 应用组织。
- API 响应结构需要稳定，方便前端依赖。

## ADR-005：第一版使用 SQLite

**日期：** 2026-05-09

**决策：** MVP 使用 SQLite 作为本地数据库。

**原因：**

- 单人本地项目部署简单。
- 不需要额外数据库服务。
- 足以支撑第一版日频数据、回测结果和调仓建议。

**影响：**

- 数据库文件默认位于 `data/quant.db`。
- 后续只有在数据规模、并发或查询复杂度明显增加时，再评估 PostgreSQL。

## ADR-006：前端使用 React + TypeScript，而不是 Streamlit

**日期：** 2026-05-09

**决策：** 前端使用 React + TypeScript + ECharts。

**原因：**

- 用户明确希望页面更清晰，后续交互会逐步增加。
- React 更适合长期维护复杂工作台。
- TypeScript 有助于稳定 API 字段和页面状态。

**影响：**

- 前端需要独立工程。
- 早期开发成本略高，但长期可维护性更好。

## ADR-007：文档中文优先

**日期：** 2026-05-09

**决策：** 项目文档中文优先，必要技术名词保留英文。

**原因：**

- 项目主要面向中文使用者和长期个人维护。
- 中文文档降低复盘和迭代成本。

**影响：**

- 新增文档默认使用中文。
- 英文术语首次出现时尽量解释含义。
