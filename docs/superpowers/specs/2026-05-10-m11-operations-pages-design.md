# M11 前端运营化页面设计

## 1. 背景

M10 已完成三类后台增强能力：

- 参数实验跟踪：记录实验参数、指标、备注和创建时间。
- 通知渠道基础：记录本地通知消息和发送结果。
- 券商接口评估：判断是否允许进入人工小资金试点评审。

这些能力目前主要停留在后端模块和测试层。M11 的目标是把它们接到前端工作台，让用户能在页面中查看、复盘和判断，而不是只通过代码或数据库理解项目状态。

## 2. 目标

M11 目标是补齐“运营化页面”，优先展示已有后台能力，不引入真实交易、不引入真实外部通知凭证。

第一阶段页面包括：

1. 实验记录页：查看参数实验列表和详情。
2. 通知历史页：查看本地通知记录和发送结果。
3. 券商准入评估页：展示当前评估条件、失败原因和允许动作。

## 3. 非目标

M11 不做以下内容：

- 不接真实券商接口。
- 不自动下单。
- 不保存券商密码、验证码、动态口令等敏感凭证。
- 不接真实邮件、飞书、企业微信凭证。
- 不做复杂可编辑策略配置。
- 不做新的调参引擎。

## 4. 推荐推进顺序

### M11-1 实验记录 API

新增只读 API，用于前端读取参数实验列表和单条实验详情。

验收标准：

- `GET /api/experiments` 返回最近实验列表。
- 支持 `limit` 参数。
- `GET /api/experiments/{experiment_id}` 返回单条实验。
- 不存在的实验返回 404。
- API 遵守 `data + meta` 响应约定。

### M11-2 实验记录页面

前端新增实验记录页，展示实验名称、创建时间、核心指标、备注和参数摘要。

验收标准：

- 页面能展示实验列表。
- 空数据时展示清晰空状态。
- 接口失败时不崩溃。
- 能查看单条实验的参数和指标详情。
- 增加前端测试。

### M11-3 通知历史 API

新增只读 API，用于读取通知历史。

验收标准：

- `GET /api/notifications` 返回通知列表。
- 支持 `channel` 和 `limit` 参数。
- API 遵守 `data + meta` 响应约定。
- 不暴露任何外部通知凭证。

### M11-4 通知历史页面

前端新增通知历史页，展示通知标题、通道、级别、状态、时间和元数据摘要。

验收标准：

- 页面能展示通知列表。
- 支持按通道筛选。
- 空数据和错误状态清晰。
- 增加前端测试。

### M11-5 券商准入评估 API

新增只读评估 API，根据输入或默认样例返回券商准入评估结果。

验收标准：

- `GET /api/broker/readiness` 返回当前准入状态。
- 返回失败原因、允许动作和是否允许进入人工试点评审。
- 默认不返回任何自动下单能力。
- API 文案明确“不是实盘交易入口”。

### M11-6 券商准入评估页面

前端新增券商准入评估页，展示准入条件、状态、失败原因和只读动作边界。

验收标准：

- 页面明确展示“不自动下单”。
- 展示当前评估状态。
- 展示失败原因。
- 展示允许动作仅为只读能力。
- 增加前端测试。

## 5. 架构设计

后端保持现有模块边界：

- `app.experiments` 负责实验记录读写。
- `app.notifications` 负责通知记录和通道。
- `app.broker_evaluation` 负责券商准入评估。
- `app.main` 暴露只读 API。

前端保持现有页面风格：

- 继续使用投研工作台布局。
- 只新增工作台页面和 API 客户端函数。
- 不新增复杂路由库。
- 页面优先表格、紧凑卡片和详情区。

## 6. 数据流

实验记录：

```text
parameter_experiments -> GET /api/experiments -> frontend api -> 实验记录页
```

通知历史：

```text
notification_records -> GET /api/notifications -> frontend api -> 通知历史页
```

券商准入：

```text
broker_evaluation -> GET /api/broker/readiness -> frontend api -> 券商准入页
```

## 7. 错误处理

- 后端 API 使用稳定的 `data + meta` 结构。
- 列表接口空数据返回空数组，不返回错误。
- 参数非法返回 422。
- 单条资源不存在返回 404。
- 前端接口失败时展示空状态或错误提示，不阻塞其他页面。

## 8. 测试策略

后端：

- 为每个新增 API 添加测试。
- 覆盖正常返回、空数据、参数校验和 404。
- 保持不访问网络、不依赖实时行情。

前端：

- 为每个新增页面添加基础渲染测试。
- 覆盖空状态和 API 失败状态。
- 重要展示文案需要测试，特别是“不自动下单”。

全量验证：

- `uv run pytest`
- `uv run ruff check app tests`
- `uv run ruff format --check app tests`
- `npm test`
- `npm run lint`
- `npm run build`

## 9. 顺序约束

M11 必须按任务 ID 顺序推进：

1. 先做后端 API。
2. 再做对应前端页面。
3. 每轮完成后同步更新任务文档、当前迭代、更新日志和测试文档。

如果中途发现后端能力不足，应先补测试和后端能力，再继续前端页面。
