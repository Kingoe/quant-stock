# M12 数据运营增强设计

## 1. 背景

M0-M11 已完成个人 A 股多因子选股辅助系统的主要功能闭环：数据底座、股票池过滤、因子评分、组合构建、回测、前端工作台、报告导出、模拟运行、通知、实验记录和券商准入评估。

下一阶段不继续堆叠新页面，而是提升“每周能稳定使用”的能力。量化项目长期可用的关键不只是算法，而是数据是否新鲜、字段是否完整、任务是否可追溯、策略运行前是否能提前发现问题。

## 2. 目标

M12 的目标是把项目从“功能模块可运行”推进到“数据运营流程可依赖”。

核心目标：

- 明确 AkShare 和本地 CSV 两类数据源的能力边界。
- 增加可追踪的数据更新任务。
- 增加数据质量检查，识别缺失、过期和异常数据。
- 在运行策略前做前置检查，避免用脏数据生成调仓建议。
- 将数据更新、策略运行、报告生成串成一条人工可确认的每周流程。

## 3. 非目标

M12 不做以下事情：

- 不接真实券商交易。
- 不自动下单。
- 不把 AkShare 实时网络结果写入单元测试。
- 不承诺 AkShare 所有接口长期稳定。
- 不引入需要付费账号的数据源。
- 不重写已有因子、组合和回测核心逻辑。

## 4. 推荐方案

采用“数据运营增强”方案，分 7 个任务顺序推进：

| ID | 任务 | 说明 |
| --- | --- | --- |
| M12-1 | 完善 AkShare 数据源字段覆盖 | 补齐指数成分、估值、财务、交易日历等适配能力，单元测试使用 mock |
| M12-2 | 增加数据更新任务入口 | 提供后端任务入口，按数据类型触发更新并写入运行日志 |
| M12-3 | 增加数据更新日志 API | 查询最近数据更新任务、状态、耗时、错误和结果摘要 |
| M12-4 | 增加数据更新日志页面 | 前端展示更新任务列表、状态和错误信息 |
| M12-5 | 增加数据质量检查报告 | 检查数据新鲜度、缺失字段、停牌/涨跌停字段、财务披露日期等 |
| M12-6 | 增加策略运行前置检查 | 在运行本周策略前检查数据质量，不满足条件时阻止运行并说明原因 |
| M12-7 | 增加一键生成本周完整报告流程 | 串联前置检查、策略运行、通知和 HTML/CSV/Excel 报告生成 |

推荐按上述顺序执行，不跳跃。M12-1 和 M12-2 是后续任务的基础，M12-6 依赖 M12-5 的质量检查结果，M12-7 依赖前面所有能力。

## 5. 架构设计

### 数据源层

继续保留统一 `DataProvider` 接口。

- `LocalCsvProvider`：用于固定测试、手工导入、无网络回放。
- `AkShareProvider`：用于个人研究场景的数据补充。

M12 会补充 AkShareProvider 未实现的数据能力，但业务逻辑仍然只依赖统一接口，不直接调用 AkShare。

### 数据更新层

新增数据更新服务，职责是：

- 接收数据类型、日期范围、指数代码等参数。
- 调用对应 provider 获取数据。
- 使用已有 loader 写入 SQLite。
- 写入 `run_logs`，记录 pending、running、success、failed。
- 返回更新条数、跳过条数、错误摘要。

### 数据质量层

新增质量检查服务，职责是：

- 检查各数据表最新日期。
- 检查指定评分日所需数据是否齐全。
- 检查关键字段是否缺失。
- 检查财务数据披露日期是否满足避免未来函数要求。
- 输出结构化问题列表，按 error、warning、info 分级。

### 策略前置检查层

在运行本周策略前调用质量检查。

- 存在 error 时阻止运行。
- 只有 warning 时允许运行，但必须返回风险提示。
- 检查结果需要写入响应和运行日志。

### 前端页面

M12 前端新增一个页面或扩展现有“数据状态”页。推荐先扩展现有“数据状态”页，避免导航过度膨胀。

展示内容：

- 数据更新任务列表。
- 最新数据日期。
- 数据质量检查结果。
- 最近一次策略前置检查结果。

## 6. API 设计

M12 建议新增或扩展以下 API：

```text
POST /api/data/update
GET  /api/data/update-logs
GET  /api/data/quality-report
GET  /api/strategy/preflight
POST /api/reports/weekly-full
```

所有 API 继续遵守 `data + meta` 响应约定。

默认行为：

- `POST /api/data/update` 不自动定时执行，只提供手动触发入口。
- `GET /api/data/quality-report` 在空数据库下返回明确问题列表，不抛出不可读错误。
- `GET /api/strategy/preflight` 用于运行策略前检查，不直接生成调仓建议。
- `POST /api/reports/weekly-full` 只生成报告和通知，不做真实交易。

## 7. 错误处理

错误分三类：

- `error`：阻止策略运行，例如缺少评分日行情、股票池为空、财务数据无法对齐。
- `warning`：允许运行但需要提示，例如估值数据部分缺失、部分股票缺少行业。
- `info`：记录状态，例如当前数据已是最新、没有新记录可更新。

外部数据源失败时：

- API 返回 failed 状态和清晰错误摘要。
- 写入 `run_logs`。
- 不写入部分不完整数据，除非 loader 已有明确的幂等和校验机制。

## 8. 测试策略

后端测试：

- AkShareProvider 新字段映射必须使用 mock，不访问真实网络。
- 数据更新任务覆盖成功、失败、空数据和重复更新。
- 更新日志 API 覆盖状态过滤和数量限制。
- 数据质量报告覆盖空库、正常、缺失、过期、异常字段。
- 策略前置检查覆盖阻止运行、允许运行但警告、完全通过。
- 完整周报流程覆盖成功生成和前置检查失败。

前端测试：

- 数据状态页能展示更新日志。
- 数据状态页能展示质量检查问题。
- 空数据和接口失败有稳定兜底。
- 一键完整周报流程能展示成功和失败状态。

## 9. 验收标准

M12 完成时需要满足：

- 用户能手动触发数据更新。
- 用户能看到最近数据更新任务是否成功。
- 用户能看到数据质量问题，而不是只看到“暂无数据”。
- 策略运行前能识别关键数据缺口。
- 完整周报流程不会在数据不合格时继续生成误导性建议。
- 所有新增能力都有后端或前端测试覆盖。
- 文档、任务规划、测试用例和更新日志同步更新。

## 10. 风险与约束

- AkShare 免费接口可能变化，因此所有字段映射都需要 mock 测试和清晰错误提示。
- 不同数据源字段粒度不一致，必要时先保守降级，不强行补全。
- 数据质量检查不替代人工判断，只提供运行前风险提示。
- 本项目仍然定位为个人投研辅助系统，不做自动实盘交易。

## 11. 自检结果

- 无待定项。
- 无与项目约束冲突的内容。
- 范围聚焦在数据运营增强，没有引入真实交易。
- 任务顺序满足依赖关系，M12-1 到 M12-7 可以按顺序实施。
